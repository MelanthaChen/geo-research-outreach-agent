# Invitation generation reliability

The synchronous Generate endpoint remains the owner of the idempotency key and the short database commit. It renders invitation rows and builds the downloadable package outside any database transaction, then rechecks the reviewed recipient set and active template before committing. A browser timeout is reconciled by the same idempotency key; a retry returns the existing batch and never creates another one.

For larger future batches, move rendering/package preparation to a durable job table rather than keeping a web request open. The request should atomically insert a `PREPARING` batch and uniquely keyed job, then return `202` with the saved batch URL. A database-leased worker should claim bounded chunks, persist per-candidate `generated`, `skipped`, or `failed` outcomes, and transition the batch to `PENDING_REVIEW` only when all chunks finish. The worker must revalidate suppression, exact-address evidence, contact verification freshness, recipient choices, and template version at commit; it must never send messages. A retry with the same key should return the same batch/job state. Until that durable worker is deployed, the current synchronous path is idempotent and avoids long database locks, but very large batches remain subject to web-request timeouts.
