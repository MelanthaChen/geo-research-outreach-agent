# Recruitment workflow implementation

Implemented the first operational outreach-first workflow while preserving the
existing lifecycle contracts, candidate stores, campaign sidecar, and
`geo-research-integration/v1` adapter.

## Implemented features

- Extended the existing dashboard with a `Research Queue` page. It reads the
  single persistent lifecycle registry, supports server-side pagination,
  search, profile-type and consent filters, visible-record selection, detail
  inspection, and CSV export.
- Added lifecycle APIs for personalized draft creation, questionnaire
  invitations, reviewed batch approval, disabled-provider simulated sending,
  reply ingestion, withdrawal, record detail, and registry export.
- Added a deployment-ready questionnaire HTML route at `/questionnaire` and
  authenticated token ingestion at `/api/questionnaire`. Tokens are opaque,
  HMAC-bound, stored only as hashes, expiry-checked, replay-safe, and
  idempotent for duplicate responses. Conflicting responses become
  `NEEDS_REVIEW`; identity confirmation is required for automatic consent.
- Added separate consent fields for public analysis, recommendations, ongoing
  measurement, optional future contact, and website modification authorization.
- Added personalized recruitment drafts with template/profile versioning,
  preliminary-screening context, questionnaire-link injection, recipient
  validation, preview hashes, and human approval.
- Added a disabled-by-default production delivery boundary. Development can
  record only local simulated sends; approval, stale-preview, suppression,
  per-draft idempotency, and batch-size/rate-limit checks are enforced.
- Added advisory reply ingestion keyed by message/thread references and
  verified sender flag. Unsubscribe replies populate suppression; vague
  positive replies never become consent.
- The questionnaire representative email is an accountability and traceability
  field and may differ from the original invitation recipient. The reviewer
  verifies representative authorization independently; strict email equality is
  not a consent requirement. Distinct submissions for one invitation remain
  conflict-quarantined.
- GEO handoff remains idempotent and consent-gated. It does not launch audits,
  experiments, paid LLM calls, or deployments.

## UI and API routes

Dashboard UI:

- `#research-queue`: paginated unified lifecycle table, filters, selection,
  detail view, draft/invitation/simulated-send controls, and CSV export.

Read routes:

- `GET /api/research/records`
- `GET /api/research/records.csv`
- `GET /api/research/records/{profile_id}`
- `GET /questionnaire?token=...`

Write routes:

- `POST /api/recruitment/draft`
- `POST /api/recruitment/invite`
- `POST /api/recruitment/approve-batch`
- `POST /api/recruitment/send-simulated`
- `POST /api/questionnaire`
- `POST /api/recruitment/replies`
- `POST /api/research/withdraw`

All state is stored in the existing lifecycle registry model; no second
competing database was introduced. The registry is separate from the legacy
candidate databases as required by the earlier integration contract.

## Required credentials and configuration

- `RESEARCH_QUESTIONNAIRE_SECRET`: required to create invitations and accept
  questionnaire submissions. Store it in a deployment secret manager; never
  expose it to the browser.
- A production email provider credential is not configured. The current
  provider is deliberately disabled and cannot send company mail.
- A future Gmail adapter will require scoped OAuth/service credentials,
  verified sender identity, suppression/bounce access, rate limits, and an
  owner-approved production configuration separate from the existing
  allowlisted Gmail test-send endpoint.
- A real GEO Engine handoff will require scoped authenticated transport,
  TLS, idempotency keys, property mapping, retry policy, and callback/polling
  credentials.

## Public hosting requirements

Before publishing the questionnaire, provide HTTPS hosting, a stable origin,
CSRF/origin protection, secret-manager-backed questionnaire secret, privacy and
consent wording, retention policy, authenticated response ingestion, rate
limiting, abuse protection, and monitoring. Configure the questionnaire base
URL separately from the local relative URL generated by the dashboard.

## Remaining blockers

- No production email delivery or Gmail thread/watch synchronization is
  enabled.
- No public questionnaire deployment or authenticated external webhook is
  configured.
- Reply linkage currently accepts a verified-sender assertion from the adapter;
  a real Gmail adapter must independently verify message/thread ownership.
- GEO Engine transport remains local/idempotent; no network endpoint is called.
- Bulk-review UI is present for the new research queue, but production batch
  policy, suppression review, and sender authorization still require human and
  operational configuration.
- Long-term monitoring and approved report delivery remain downstream phases.

No real email was sent, no form was submitted, no service was deployed, no
paid LLM call was made, and no hotel worker, checkpoint, or existing dataset
was reset or interrupted.
